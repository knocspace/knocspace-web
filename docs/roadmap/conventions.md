## 모든 스프린트의 완료 조건

각 스프린트 문서의 완료 조건에 **더해서** 아래를 매번 확인합니다.

### 코드

- [ ] `npm run build` 통과 (타입 검사 포함)
- [ ] `npm run lint` 경고 0
- [ ] 새 기능에 테스트 1개 이상 추가

### 화면

- [ ] 라이트 모드와 다크 모드 양쪽 확인
- [ ] 로딩 / 에러 / 빈 화면 처리
- [ ] 마우스 없이 키보드만으로 해당 기능 완주 가능

### 디자인 규칙 (DESIGN.md)

- [ ] 코드에 하드코딩된 hex 색 0개
- [ ] SEED 컴포넌트에 `!important`나 자손 선택자로 덮은 곳 0개
- [ ] 허용 목록 밖의 `--seed-*` 변수를 재정의한 곳 0개
- [ ] 새 변수는 전부 `--knoc-` 접두사
- [ ] 문구가 해요체이고, 사과하지 않고, 느낌표가 없음
- [ ] UI에 이모지 없음 (사용자가 고르는 문서 아이콘만 예외)

### 경계

- [ ] `src/components/` 안에 `useQuery` import 0개
- [ ] `src/api/` 밖에 `localStorage` 직접 호출 0개

## 문서 관리 규칙

문서도 유지보수 대상입니다. 늘리기 전에 아래를 지킵니다.

**1. 완료된 스프린트 문서는 갱신하지 않고 지웁니다.**
`sprint-1.md`는 다 쓰면 버리는 체크리스트입니다. 끝나면 삭제하고, 남길 게 있으면 규칙으로 바꿔서 `architecture.md`나 이 문서로 옮깁니다. 안 그러면 다 끝난 체크리스트가 계속 쌓입니다.

**2. "지금 상태"는 `ROADMAP.md` 한 곳에만 적습니다.**
상태를 적은 문서는 커밋할 때마다 틀려집니다. 상태를 두 곳에 적으면 어느 쪽이 맞는지 알 수 없게 됩니다.

**3. 코드나 git이 이미 말해주는 것은 적지 않습니다.**
폴더에 뭐가 있는지, 지난주에 뭘 고쳤는지는 문서로 관리하지 않습니다.

**4. 출처가 있는 값은 옮겨 적지 않고 링크합니다.**
색·치수·문구는 `DESIGN.md`, 타입은 `src/types/api.ts`가 유일한 출처입니다.

**5. 먼 계획은 자세히 쓰지 않습니다.**
Sprint 5 이후는 개요만 두고, 시작 직전에 상세하게 풉니다. 미리 쓴 상세 계획은 시작할 때쯤 대부분 틀려 있습니다.

## 커밋 규칙

```
feat:      기능 추가
fix:       버그 수정
refactor:  동작 변화 없는 정리
chore:     설정·의존성
test:      테스트
docs:      문서
```

한 커밋은 하나만 합니다. 기능과 리팩터링을 섞지 않습니다.

## 스프린트 시작·종료 절차

**시작할 때**

1. 해당 스프린트 문서를 읽습니다
2. 선행 조건이 충족됐는지 확인합니다 (특히 디자인 결정 사항)
3. UI 작업이 있으면 `DESIGN.md`를 다시 읽습니다

**끝낼 때**

1. 스프린트 문서의 완료 조건 체크
2. 이 문서의 공통 완료 조건 체크
3. E2E 1개 추가 (Sprint 4부터)
4. 다음 스프린트 문서를 상세하게 풀어 씁니다 (Sprint 5부터)
