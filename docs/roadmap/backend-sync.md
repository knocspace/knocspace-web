# 백엔드 연동 계약

← [로드맵으로](../../ROADMAP.md)

`knocspace-api`와 이 레포가 언제 무엇을 주고받는지에 대한 기준입니다.
**타입의 실제 출처는 `src/types/api.ts` 하나입니다.** 여기에는 일정과 합의 항목만 적습니다.

---

## 언제 서로를 기다리나

| 프론트 | 백엔드에 필요한 것 | 없으면 |
|---|---|---|
| F1 | 없음 | — |
| F2 | B1의 **Page 도메인 설계 초안** (필드 이름 수준) | 초안 없이 진행하고 F4에서 대조 |
| F3 | 없음 | — |
| **F4** | **B3 완료 — Page CRUD 엔드포인트 배포** | F4를 미루고 F8(검색)을 먼저 진행 |
| **F5** | **B4 완료 — 인증과 User 도메인 배포** | F5를 미루고 F8을 먼저 진행 |
| **F6** | **B5 — Database 도메인과 CRUD** (새 설계) | 진행 불가에 가깝습니다. 도메인 모양이 안 정해지면 mock을 만들어도 F4처럼 갈아끼울 수 없습니다 |
| **F7** | **B6 — Database 쿼리** (필터·정렬·커서) | 표는 되지만 보드의 필터·정렬이 안 됩니다 |
| F8 | **B7** — 검색과 휴지통 | mock(부분일치)으로 화면만 진행 |
| F9 | **B8** — 파일 업로드 (presigned URL) | mock(IndexedDB)으로 진행 |
| F10 | **B9** — WebSocket 서버 | 진행 불가 |

프론트는 F3까지 mock으로 완결되므로, **백엔드 일정이 밀려도 3주간은 영향이 없습니다.**
F4·F5가 막히면 순서를 바꿔서 F8(검색)을 먼저 하고 돌아옵니다. mock/실서버 전환 스위치를 남겨두는 이유가 이것입니다.

**F6~F7(데이터베이스)만은 백엔드를 앞질러 갈 수 없습니다.** Page·User와 달리 도메인이 새로 설계돼야 해서, 프론트가 mock으로 먼저 만들면 그 mock이 곧 프론트가 정한 도메인이 됩니다. 그래서 검색·파일보다 앞에 두고, **B5 설계를 F5 진행 중에 같이 시작합니다.**

## F2 시작 전 합의할 것

Page 도메인의 **모양**만 맞춥니다. 엔드포인트는 아직 없어도 됩니다.

- [ ] id 타입 — UUID / ULID / 숫자. 문자열로 통일할지
- [ ] **id를 클라이언트가 만들어 보내도 되는지** — 낙관적 업데이트가 여기에 달려 있습니다
- [ ] 필드 이름 — `parentId` `workspaceId` `updatedAt` `deletedAt` `position`
- [ ] 널 허용 — `parentId` `icon` `deletedAt`
- [ ] 날짜 형식 — ISO 8601 UTC 문자열
- [ ] 삭제가 soft delete인지 (`deletedAt`만 채우는지)
- [ ] 본문(`content`)을 그냥 JSON 덩어리로 보관하는지, 블록 단위로 쪼개는지
  - 프론트는 **덩어리**를 전제로 만듭니다. 쪼갤 거면 F2 전에 알려주세요
- [ ] 트리를 한 번에 주는지(`getPageTree`), 자식만 주는지
- [ ] 응답 껍데기 — `{ data }` 로 감싸는지 그냥 주는지

## F4 시작 전 확인할 것

이제 실제 응답과 대조합니다.

- [ ] 엔드포인트 경로와 메서드 전부
- [ ] 에러 응답 모양 — 프론트의 `ApiErrorCode` 6종과 상태 코드가 어떻게 대응되는지

  | 코드 | 상태 |
  |---|---|
  | `not_found` | 404 |
  | `version_conflict` | 409 |
  | `unauthorized` | 401 |
  | `forbidden` | 403 |

- [ ] **낙관적 잠금** — `version` 필드가 있는지, 요청에 어떻게 실어 보내는지(본문 / `If-Match` 헤더)
- [ ] 저장이 부분 수정(PATCH)인지 전체 교체(PUT)인지
- [ ] 페이지네이션 방식 — cursor / offset (F6 표, F8 검색에 그대로 씁니다)
- [ ] 인증 없이 접근할 개발용 워크스페이스가 열려 있는지 — **F4에는 로그인이 없습니다**
- [ ] CORS 허용 도메인

## F5 시작 전 확인할 것

- [ ] 로그인 방식 — 이메일/비밀번호, OAuth, 매직 링크
- [ ] 토큰 전달 — httpOnly 쿠키 / Authorization 헤더
- [ ] 갱신 방식과 만료 시간
- [ ] 권한 모델 — 워크스페이스 역할과 페이지 단위 공유가 어떻게 겹치는지
- [ ] `User.color`를 서버가 정하는지 클라이언트가 정하는지 (F10 커서 색)

---

## F6 시작 전 합의할 것

**Page·User와 달리 이건 새 도메인입니다.** F5를 진행하는 동안 백엔드와 같이 설계합니다. mock을 먼저 만들지 않습니다 — 만들면 그게 곧 도메인이 됩니다.

- [ ] `Database` / `Property` / `Row` / `View` 중 무엇을 1급 엔티티로 두는지
- [ ] 속성(컬럼) 정의를 어디에 두는지 — 데이터베이스에 붙은 스키마인지, 행마다 자유인지
- [ ] 속성 7종(텍스트·숫자·선택·다중 선택·날짜·체크박스·URL)의 저장 형태와 `CellValue` 표현
- [ ] 선택지(옵션) 목록을 속성이 갖는지, 별도 테이블인지
- [ ] 속성을 지우면 그 값이 어떻게 되는지 (같이 지움 / 남김)
- [ ] 행이 페이지인지 — 행을 열면 문서가 뜨는 노션 동작을 지원할지. **`Row`와 `Page`의 관계가 이 도메인에서 제일 큰 결정입니다**
- [ ] 필터·정렬을 서버가 처리하는지 (`queryRows({ filter, sort, cursor })`)
- [ ] 뷰(표/보드) 설정을 서버가 저장하는지, 클라이언트 로컬인지
- [ ] 5000행 페이지네이션 방식

---

## 어긋났을 때

**프론트에서 변환 함수로 덮지 않습니다.** 한 번 만들면 영원히 남고, 그 뒤로 타입 두 벌을 관리하게 됩니다.

1. 어느 쪽이 맞는지 정합니다 (보통 도메인을 가진 백엔드가 맞습니다)
2. 틀린 쪽을 고칩니다
3. `src/types/api.ts`에 반영하고 백엔드에 공유합니다
